# AI 视频生成平台 · MVP 方案与架构 v0

> 状态：讨论稿 v0（2026-09-20）。定位、选型、MVP 边界已达成共识，本文是首个正式架构方案。
> 原则：单用户、单并发、端到端；简化基础设施，不简化管线质量。

## 1. 定位与已定结论

- **路线**：确定性代码渲染（HTML 合成 → MP4），不用视频生成模型。做信息密度高的品类：科普、解说、宣传。
- **引擎**：HyperFrames（HeyGen 开源，Apache-2.0，HTML+GSAP → 确定性 MP4，变量批量渲染，lint/check 质量门禁，0.8.x 需锁版本）。备选 Remotion / Revideo，渲染层做抽象对冲。
- **用户**：个人创作者 + 营销人员，功能上融合为同一产品（差异只在打包/组织层，后加）。
- **MVP**：单用户端到端可用。验收：真实创作者无工程师在场，粘贴文章 → 10 分钟内拿到 60–90s 带字幕 BGM 成片；10 次生成免修复可用 ≥7；至少一条愿意发到自己账号。

## 2. 两个交互决策（v0 钉死）

### 2.1 输入形式：粘贴文本为主，主题一句话为辅（二期）

理由：
- 科普/解说的原料是**内容**。文章→视频是确定性最高的转换：信息密度和结构现成，LLM 发挥空间在视觉层而非事实层，幻觉风险最小。
- 一句话主题需要 LLM 凭空写全部文案，质量与事实性不可控，放到二期。
- 链接解析（公众号/网页抓取）有反爬与合规复杂性，MVP 用"粘贴正文"绕开，链接输入二期加（readability 抽取）。

### 2.2 交互形态：分镜文档（内容层确认）+ 一键生成 + 低清草稿 + 段级重生成

两道确认门，各设在用户判断力最强的地方：

- **门 1 · 分镜文档（内容层）**：AI 先产出分镜文档——每段 = 旁白文案 + 简短画面提示（人话）+ 时长估计。用户直接改文字、调段序、删减内容，确认后进入生成；也可以不改直接点确认（等效一键）。用户对"内容"能做高质量判断，因为这是他的素材。
- **门 2 · 低清草稿（视觉层）**：画面好坏无法从文字预判，视觉不设文字确认门，用 90 秒内出的低清草稿确认；不满意整条或按段重生成。visual_brief 在分镜文档中可见但不要求逐段确认。

**时序原则（单一时间基准）**：每个项目先确定"谁拥有时间轴"并声明在分镜文档（timing_basis）。科普/解说默认**旁白驱动**：先 TTS 得到每段实际时长与逐词时间戳，合成物按这些时长生成，逐词高亮字幕直接消费时间戳。宣传/卡点类可**音乐驱动**：先定 BGM 与节拍网格，旁白适配节拍。不变的约束是**基准产物必须先于适配它的产物**——"先生成画面再配音"必然时长错位、旁白被裁。基准的选择由 AI 按项目判断并写入分镜文档。音效在合成物生成时按节拍点（转场/数据揭示/强调）自动布点，不设独立工序。

**黄金路径（v0 定义）**：

```
粘贴文章正文 → 选风格（v0 预置 3 套）
  → AI 生成分镜文档（分段旁白 + 画面提示 + 时长估计）
  → 门1：用户改文案/调结构/删减 → 确认（或直接确认 = 一键）
  → TTS（每段音频 + 逐词时间戳）→ 生成合成物 → lint/check
  → 门2：90 秒内出 9:16 低清草稿（含字幕、旁白、BGM、音效）
  → 满意 → 点"出片" → 1080p 高清渲染（1–3 分钟）→ 下载
  → 不满意 → 整条重生成 / 指定段重生成
     （改文案 → 该段回到 TTS 重跑；只改画面 → 只重做该段合成物）
```

### 2.3 流程模型：硬约束、默认流程、AI 裁量

先后顺序不写死为产品向导，分三层：

- **硬约束（平台强制，AI 不可裁量）**：依赖方向（时间基准产物先行于适配产物）；渲染前必过 lint/check 门禁；确定性规则（无网络、无时钟）；产物 schema（分镜表/合成物/报告）。
- **默认流程（黄金路径 = 缺省计划）**：门 1 → TTS → 合成物 → 门 2 → 高清出片。项目无特殊声明时按此执行。
- **AI 裁量（按项目判断，写入分镜文档"制作方案"区）**：时间基准（旁白/音乐）；交互轮次（追问口吻与长度，或直接一键）；分段策略与时长分配；音效密度；草稿密度（先出前 3 段验证风格，还是整条）。

落地节奏：M0/M1 按默认流程实现（可靠、可测），但分镜表 schema 从第一天携带 `timing_basis` 与 `plan` 字段；M2 起 planner 逐步接管可裁量项。改进产品的方式是换 AI 的计划，不是改应用的代码。

## 2.4 竞品参照：svganimate.ai

同赛道产品，双模式结构：**HTML 视频模式**（输入主题/描述 → 自动生成逐字稿、分镜、HTML 场景画面、旁白、字幕，分镜可编辑）+ **SVG 动画模式**（单场景：logo/文字/地图/3D/理工科科普等十多种类型）。目标场景：知识讲解、课堂教学、故事讲解。积分制试用，导出 GIF/MP4/HTML。

**模仿的部分**：
- **双产品面结构**：完整视频（主管线）+ 单场景动画（低门槛入口，兼作风格组件/模板的积累来源）。单场景动画列为 M2+ 产品面——复用同一引擎与合成物规范，增量在 UI 与提示词工程。
- 场景化营销话术（知识博主/教师/故事讲述者）与"无需编码、无提示词门槛"定位。
- 积分制试用（注册送积分）。
- "脚本→分镜、可编辑"——印证门 1 设计方向正确。

**差异化（对手弱点 = 我们主打卖点）**：
- **确定性渲染**：对手 FAQ 承认导出视频可能与网页预览不一致、需提供"直接录屏"兜底。我们 HyperFrames 逐帧 seek 确定性渲染，预览=成片。这是第一技术卖点。
- **内容来源**：对手主打"主题→凭空生成文案"（事实与质量风险）；我们以粘贴文章为主输入，内容是用户的，门 1 可编辑。
- **段级重生成**：一段 = 一个 sub-composition，精准重做；对手无此能力的证据。
- **质量门禁**：lint/check + 自修复循环，成片成功率可度量。

**不模仿**：录屏兜底（确定性渲染使不需要）；GIF/HTML 页面导出（低优先级）；单场景类型大而全（先聚焦科普/解说管线）。

## 3. 模块架构

```
┌─────────────────────────────────────────────────────┐
│ Web 前端（Next.js）                                    │
│  贴文表单+选风格 / 分镜编辑确认 / 进度 / 草稿预览 / 段级重试 / 下载 │
└──────────────────────┬──────────────────────────────┘
                       │ HTTP / SSE（进度推送）
┌──────────────────────▼──────────────────────────────┐
│ API 服务（Node.js，与前端同仓）                         │
│                                                      │
│ ① 编排器 Orchestrator（agent 循环，每步落盘可重放）      │
│    a. 脚本生成：文章 → script.json（分镜表）  [LLM]     │
│    b. TTS：每段旁白 → 音频 + 逐词时间戳      [TTS 供应商] │
│    c. 合成物生成：script.json + 风格档 → HyperFrames    │
│       HTML（每段 = 一个 sub-composition）    [LLM]     │
│    d. 质量门禁：hyperframes lint/check + 快照审查       │
│    e. 自修复循环：读诊断 → 定点修改 → 重查（≤3 次）      │
│                                                      │
│ ② 渲染器 Renderer（MVP：本机单并发子进程，调 hyperframes │
│    CLI；draft 低清低帧率 / delivery 1080p）             │
│                                                      │
│ ③ 项目存储：SQLite（项目/任务/产物元数据）+ 文件系统     │
│    （合成物、音频、渲染产物，按 project_id 组织）         │
│                                                      │
│ ④ 媒体资产：预置风格档（色板/字体/组件）、BGM 库、        │
│    图标库，全部本地化，杜绝渲染时网络请求                 │
└─────────────────────────────────────────────────────┘
```

关键设计点：

1. **分镜表（script.json）是系统的中枢数据结构**：头部 `{ timing_basis(narration|music), plan(AI 的制作方案与裁量项), style_id }` + `segments[] = { id, narration, visual_brief, duration_hint, tts_asset }`。它同时是门 1 用户编辑的对象、AI 裁量的载体、TTS 的输入、合成物生成的输入、段级重生成的寻址单元、UI 展示分段的依据。
2. **音频先于画面**：管线顺序固定为 脚本 → TTS → 合成物。段时长以 TTS 实际音频长度为准（duration_hint 仅是分镜阶段估计），逐词高亮字幕直接消费 TTS 时间戳；音效在合成物内按节拍点布点。
3. **一段 = 一个 HyperFrames sub-composition**：`index.html` 只做组装与全局转场。段级重生成 = 只重跑该段的 TTS（若文案变）和合成物（画面变）+ 重新组装，隔离性好。
4. **编排器每步产物落盘**（script.json、audio/、compositions/、check 报告），失败可从任意步重放——这也是将来做批量和审计的地基。
5. **渲染层接口**从第一天抽象为 `submit(project, quality) → job → mp4`，MVP 实现是本机子进程，将来换容器集群/Lambda 不动上层。
6. **确定性约束**：合成物内禁止网络请求/运行时时钟，字体图标全部本地资产——沿用 HyperFrames determinism 规则，平台在门禁里复查。

## 4. 数据模型（v0 草案）

```
Project   { id, input_text, style_id, aspect, status, created_at }
Segment   { id, project_id, idx, narration, visual_brief, duration_hint,
            tts_path, comp_path, version }
RenderJob { id, project_id, quality(draft|delivery), status, output_path,
            started_at, finished_at, error }
Style     { id, name, tokens(JSON: 色板/字体/组件预设/动效偏好), builtin }
```

## 5. 技术栈（v2 选型，按团队技能 Java/Go/Python/Vue）

> **2026-09-20 已定稿为独立选型文档：`docs/tech-stack.md`（含库级清单、LLM/TTS 决策树、M0 验证清单）。本文表格保留为决策背景，冲突处以选型文档为准。**

总原则不变：**渲染引擎当黑盒 CLI（Node 22 + FFmpeg 只是运行时依赖，团队不写 TypeScript）、两个进程一个仓库、一切服务于 M0**。

| 层 | 选型 | 理由 |
|---|---|---|
| 前端 | **Vue 3 + Vite + Naive UI**（或 Element Plus） | 团队技能；表单/分镜卡片编辑/进度/视频预览都是标准组件形态；SSE 用 EventSource |
| API + 编排 + 渲染 worker | **Go（单二进制，一个进程两种角色）** | 子进程管理（exec 调 hyperframes CLI）和长任务循环是 Go 强项；单文件部署到渲染服务器最省事；SSE 简单；内存小 |
| AI 旁路（可选） | **Python（FastAPI）**：自托管 CosyVoice TTS / funASR 时间戳对齐 | 仅当不用云 TTS 或需要 ASR 兜底时出现；MVP 用火山引擎云 TTS 则此服务可以为零 |
| Java | **不进 MVP** | Spring Boot 在本项目无独特优势、迭代更重；例外：若个人对 Java 生产力远高于 Go，可用 Spring Boot + Spring AI 替换 Go，架构不变 |
| LLM 接入 | Go 直调 OpenAI 兼容 API（sashabaranov/go-openai 或 eino）+ JSON Schema 校验；或并入 Python 侧用 pydantic/instructor | 分镜表结构化输出：Go 侧校验 LLM 返回的 JSON 对 schema；M0 实测 GLM/DeepSeek/Qwen 定两档 |
| 编排 | Go 自写循环：生成 → schema 校验 → lint/check（--json）→ 读诊断 → 修复（≤3 次），每步落盘 manifest | 管线是"线性步骤+重试"；不用任何 agent 框架 |
| 存储 | SQLite（Go: database/sql + sqlc，或 ent）；媒体产物走文件系统 | 零运维；上量迁 Postgres 只换连接串 |
| 任务队列 | SQLite jobs 表 + Go 协程轮询（单并发） | 不需要 Redis |
| 渲染 | Go `exec.CommandContext` 调 hyperframes CLI（锁版本），--quality draft / looks / --docker | 对应 `submit(project, quality) → job → mp4` 抽象 |
| TTS | 火山引擎（豆包音色）为主，CosyVoice 自托管备选，funASR 时间戳对齐兜底 | M0 实测逐词时间戳 |
| 校验/测试 | go test + M0 语料回放脚本（10 篇文章 → manifest：通过率/耗时/成本） | 所有 LLM 输出当外部输入校验 |
| 日志 | zerolog/slog 结构化 + 每项目 run manifest 落盘 | 支撑"从任意步重放" |
| 部署 | MVP 本机开发；渲染以 Linux 容器为准（容器内装 Node 22 + FFmpeg + hyperframes 锁版本），Windows 经 Docker Desktop/WSL2 | Chrome/ffmpeg 在 Linux 容器内稳定可复现 |

**明确不用**：LangChain 系（线性管线不需要 agent 图框架）、Redis/RabbitMQ/K8s/微服务（单用户阶段纯负担）、TypeScript 应用代码（Node 仅作渲染运行时依赖）、MongoDB。

**仓库结构**（无 workspace 工具，目录即模块，第一步 git init）：

```
webpage-video-agent/
  web/           # Vue 3 + Vite：表单 / 分镜编辑 / 进度 / 预览 / 下载
  server/        # Go：API + SSE + 编排循环 + hyperframes 子进程渲染 + jobs
  ai/            # Python 旁路（可选，M0 可为空）：CosyVoice / funASR
  data/          # 运行时产物（gitignore）：projects/<id>/{script.json, audio/, compositions/, renders/}
  docs/          # 方案文档
```

## 6. 里程碑

- **M0 管线打通（1–2 周，无 UI）**：一个 CLI 脚本串起 文章 → script.json → TTS → 合成物 → lint/check → draft 渲染 → delivery 渲染。产出：10 篇真实文章的成片 + 单条耗时/成本/一次通过率数据。**这是整个项目最大的技术风险点，最先验证。**
- **M1 单用户可用（2–4 周）**：Vue 3 贴文表单 + 分镜文档编辑/确认页（门 1）+ 进度 + 草稿预览（门 2）+ 下载 + 整条重生成；3 套预置风格；9:16。达标即 MVP 验收。交互形态的静态规格见 `demo/ui-demo.html`（纯前端可点击演示，Vue 3，已端到端验证）。
- **M2 段级重生成 + 种子试用（2–3 周）**：段级重试 UI、16:9 双画幅、10 名真实创作者试用，收集"10 次生成可用率"和"发出率"。

## 7. 风险与对冲

| 风险 | 对冲 |
|---|---|
| HyperFrames 0.x API 变动 | 锁版本；渲染层与合成物规范薄封装；关注 release note |
| LLM 写合成物一次通过率低 | check JSON 诊断驱动自修复循环（≤3 次）；分镜表分段隔离爆炸半径；积累失败模式进 prompt 库 |
| 渲染耗时超预期（无头浏览器逐帧） | draft 用低分辨率/低帧率；delivery 排队异步化；必要时容器并行 |
| 中文 TTS 逐词时间戳不可得 | 降级到 ASR 反打时间戳（whisper 类） |
| 国内网络依赖（npm/fonts/TTS） | 全部资产本地化 + 供应商国内可用性作为选型硬条件 |
| 单条成本不可控 | M0 实测 LLM+TTS+渲染成本，定价前建立单条成本账 |
